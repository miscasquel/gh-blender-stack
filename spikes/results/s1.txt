`solves` climbing one per round is the part that matters: `SolveInstance` really
ran for each message, triggered from the background socket thread through
`OnPingDocument().ScheduleSolution(10, ...)` and `ExpireSolution(true)`. Replies
came back in 20–65 ms. This block was the **save-and-reopen** document: the
component had been saved to a `.gh` file, the editor closed, and the file
reopened, which is why `solves` restarts at 1.

An earlier identical pass (also five rounds, solves 2..6) is at 284.961 of the
raw log.

The component detected the server going away, backed off, reconnected on its own,
and resumed solving. No dialog at any point; everything surfaced as runtime
messages and the component's own bubble (`connected, s=6, n=1`).

## What the four fixes were

1. `GetData("On")` → `"Enabled"`: `IGH_DataAccess` matches the parameter **name**,
   not the nickname.
2. `SetData("s")` → `"solves"`: the same trap on the output side.
3. The reply was queued during `SolveInstance` but only sent after the read loop
   received another frame — a deadlock. A dedicated sender thread
   (`AutoResetEvent` + `WaitHandle`) now sends replies independently, and each
   connection's sender is retired before its socket is disposed, so a stale
   sender cannot dequeue and drop a reply.
4. `ScheduleSolution(0, …)` coalesced and the delegate was silently dropped, so
   only the first message ever solved. A 10 ms delay is reliable. The spike's
   nonce counter is also reset per connection, or a reconnect's round 1 looks
   "already answered" and never gets a reply.
